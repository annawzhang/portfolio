逐场景 · 版本内演进细节（面试深挖用）

S1 锁单绩效达成

模块：atomic_metrics + derived_metrics · 贯穿 V1.0 → V2.0
  • V1.0：net_lock_order + perf_target 达成率排名，输出城市部净锁单汇总
  • V1.3：叠加 A4 同店 YoY（net_lock_yoy / net_lock_yoy_rate），区分同店下滑 vs 新店增量
  • V1.5：attribution.py 拆解「净锁单较基准低 X%，最大拖累环节是 Y」
  • V2.0：YoY 下滑成为 must_win 第四路信号（weight_yoy_decline=10，阈值 -20%）

S2 漏斗健康度诊断 ⭐ 调整最多

模块：diagnosis.py → compute_s2_health_score()
  • 方案 pivot：Logistic 意向评分 → Z-score 多因子加权（可解释、可调参）
  • V1.0：6 因子加权，输出 health_score (0–100) + health_level（优质/中等/流失严重）
  • V1.1 权重 v2：td_to_lock_rate 30%→35%，ppl_conversion 25%，open_to_td_rate 15%；新增 bottleneck 卡点标签（开启→试驾弱 / 试驾→锁单弱 / 退订损耗高）
  • V1.1：health_thresholds 中等线 40→45（线下复盘：<45 门店已感「明显跑单」）
  • V1.4：S8 线索层接入后，漏斗从「客流→商机→试驾→锁单」扩展为「线索→排程→试驾→锁单」完整链路
  • V1.5：attribution 按环节贡献拆解（如城市部 B：试驾→锁单拖累 72%）
  • V2.0：health_level=「流失严重」→ must_win 信号 #1（weight_churn=30）

S3 渠道结构诊断

模块：scenarios.py → compute_s3_channel_structure()
  • 方案 pivot：Logistic 回归系数 → BCG 矩阵 + DC attribution 归因工具
  • V1.0：输出 channel_dominant（如「线下地推(50%)」）、channel_diversity 多样性指数
  • V1.0：识别单一渠道过度依赖（占比 >70%）门店清单
  • V1.5：attribution 支持按城市部拆解「客流→商机」环节差距
  • V1.4 协同：S8 PB 渠道 tag（门店/网店/官方/外展/推荐）比 DC ab_* 更细，用于线索层分渠道

S4 PPL 过程管控 ⭐ 阈值迭代最细

模块：diagnosis.py → compute_s4_ppl_alerts()
  • 方案 pivot：Logistic → 5 条阈值规则引擎（红黄绿灰四级）
  • V1.0：5 规则 — 无长期跟进 / 无效跟进>15% / 高PPL异常 / 退订24H跟进<60% / 试驾质量<70
  • V1.2：阈值全部外置 config.yaml → ppl_alert.*，支持 --sensitivity 扫描
  • V1.3 B1：DC 403 无 lock_24h_follow_rate 权限 → 改用「3 天内锁单-跟进间隔」代理指标
  • 参数校准：follow_intensity 0.30（大盘 ~0.5）；long_follow 0.005（大盘 ~2.1%）；min_ppl 200（避免小店误伤）
  • V2.0：ppl_alert_level=「红」→ must_win 信号 #2（weight_ppl_red=35，最高权重）；PPL 红 + 池子≥200 → pipeline_bonus +10

S5 车型产销结构

模块：scenarios.py → compute_s5_series_analysis()
  • V1.0：series_role（主力/重要/边缘/无量）、series_efficiency（🚀效率高/🔻效率低/平均水平）
  • V1.0：识别「⚠️ 单一主力」风险（单车型锁单占比 >60%）
  • V1.2：series_weights 写入 config.yaml，支撑目标分摊（i6/L6 各 30%）
  • V2.0：must_win 按 store×series 单元打分，取得分最高车型为「焦点车型」

S6 新车上市诊断 · V1.2 新增独立场景

模块：new_product.py → compute_s6_new_product()
  • 方案 pivot：双 ML 模型 → 趋势曲线 + 大盘同期对标
  • V1.0：config 中 S6_customer_flow 仅占位（客流类），未独立成场景
  • V1.2 重构：独立 new_product.py；追踪 X04(i6)/X13(新L8)/X11(新L9)；输出渗透率/试驾锁单率/爬坡 verdict
  • 实例：新 L6 上市 35 天渗透率 76%；新 L9 渗透率 25% 判定「渗透偏低」
  • 飞书卡片：S6 区块单独展示「🚗 新品爬坡」摘要

S7 异常预警 · 从报警到分派到决策

模块：scenarios.py + alert_taxonomy.py + must_win_list.py
  • 方案 pivot：XGBoost → 三层规则（阈值 + 环比 + Z-score）
  • V1.0：anomaly_level 红/橙/绿；anomaly_msg（如「净锁单日均环比降 59%」）
  • V1.2 A2：alert_taxonomy 5 类病因分类 → alert_category + alert_owner + alert_priority (P1/P2/P3)
  • V1.3：接入 prev_df 环比检测（daily_drop 40% / daily_surge 50% / td_lock_rate_drop 8pt）
  • 参数：zscore_threshold 1.8；daily_drop 0.4（城市部：「掉四成必须当天介入」）
  • V2.0：异常红/橙 → must_win 信号 #3/#4（weight 25/15）；与 S2/S4 叠加 ×1.25

S8 线索层漏斗 · V1.4 新增扩展场景

模块：leads_funnel.py · 数据源 PB view2486（非 DC）
  • 背景：DC 漏斗从「客流→商机」开始，缺线索层；邀约是最大瓶颈但无数据
  • V1.4：影刀 RPA 每日拉 PB → funnel_probe_*.json → enrich_wide_with_leads() 左连接宽表
  • 新增 8 列：leads_cnt / leads_appoint_cnt / leads_attempt_cnt / leads_lock_cnt + 4 个转化率
  • 业务结果：识别邀约瓶颈，漏斗邀约率 24% → +1.8pp
  • 简历「5 环节漏斗」：线索→排程→试驾→锁单 + DC 后段 = 完整 5 环节

A4 · YoY 同店同比 · V1.3 横切场景

模块：yoy.py · 非独立 S 场景，为 S1/S2 提供对比维度
  • V1.3：拉 2025-08 历史宽表（512 行）；compute_yoy() 输出 net_lock_yoy / store_status_yoy
  • 分类：同店 / 新店/新增 / 关店/停售 / 无变化 — 避免新店冲量掩盖同店下滑
  • V2.0：同店 + YoY<-20% → must_win 第四路信号

V2.0 决策层 must_win_list · 消费 S2+S4+S7+YoY

模块：must_win_list.py · 第 14 个引擎模块（决策层，不改 S 算法）
  • 核心逻辑：四路信号打分 → 复合紧急分 → store_tier 分层 → 各层 Top N 配额 → 绑定 Narrative 动作 → 10 家 Treatment 输出
  • 分层配额：一级（MTD≥10）3 家 · 二级（5–9）4 家 · 三级（2–4）3 家；Control 组同层抽取
  • 算分示例：流失(+30) + PPL红(+35) + 异常橙(+15) = 80 × 1.25(三信号) + 10(pipeline) = 110.0
  • AB 设计：Treatment Top10 触达 vs Control 接近分数不触达；主指标清单执行率 → 次指标锁单转化率
  • 产品定位：S 场景回答「哪里有问题」→ must_win 回答「本周先救谁、做什么」

面试口述 · S 场景迭代 + 产品思维（45 秒）

我的产品经历了三次关键 pivot：第一次是建模方案，S1–S7 全部从 ML 黑盒改为可解释的规则模型——S2 用 Z-score 加权、S4 用阈值引擎、S7 用三层预警，因为 DC 是聚合数仓不是明细数仓。
